# Decisions

| Decision | Reason |
| --- | --- |
| The solution is customized for Polaris-style enterprise applications, not a generic conversion tool. | The POC is intended to preserve enterprise-specific architecture and modernization policy. |
| HealthClinic.biz is only a public reference application for the POC. | It provides an inspectable legacy flow without representing the Polaris product itself. |
| The POC will support one selected legacy ASP.NET MVC Dashboard flow first. | A bounded flow permits evidence-led discovery and later validation before broader scope. |
| Neo4j is the source-of-truth code/UI knowledge graph. | Code and UI relationships require a durable, queryable authoritative representation. |
| Graphiti is shared team/agent working memory, not the source-of-truth code graph. | Agent context is operational memory and must not replace evidence-backed code knowledge. |
| LangGraph orchestrates the workflow; LangChain manages LLM schemas, retrieval, and structured outputs. | This separates workflow control from model-facing integration concerns. |
| The first runnable target will be Angular 22 Nx modular monolith. | It is the stated target architecture for the initial modernization POC. |
| Step 1 discovery is limited to the requested Dashboard, Shared, Controllers, and Models paths. | The source boundary prevents unsupported conclusions from client-side code outside the approved scope. |
| The Dashboard Razor page is treated as a protected shell, not as proof of its detailed feature UI. | The inspected server views delegate navigation/content to client-side elements outside the selected scope. |
| The current Git repository root is the solution root. | Step 2 explicitly eliminates the nested `solution/` folder so recovery files, implementation, and Git history have one canonical root. |
| Step 2 uses Tree-sitter JavaScript, HTML, and C# grammars without a regular-expression source-parser fallback. | Deterministic, reproducible source facts require syntax-tree evidence and a clear failure mode if a grammar is unavailable. |
| Step 2 writes source inventory, facts, graph, and summary artifacts as versionable JSON/Markdown. | Later graph loading and review require durable evidence with source path, lines, hashes, extraction method, and confidence. |
| The knowledge graph will be transformed into PRDs, epics, features, user stories, acceptance criteria, and traceability links before code generation. | Business approval must be based on traceable discovered behavior. |
| Customer Figma designs are optional target-design input. | Figma defines target look and design tokens; the knowledge graph remains the evidence source for existing behavior and APIs. |
| Existing approved Angular shared components/design systems must be discovered before generation. | Reuse avoids duplicate components and preserves approved design standards. |
| A target architecture assessment, diagram, ADR, Nx boundaries, and migration plan precede Angular generation. | Architecture must be reviewable before code changes are generated. |
| Target architecture is evidence-based and rule-driven, not LLM-only. | Standard Angular, Nx modular monolith, microfrontend, SSR/hydration, BFF, Signals, typed forms, security, and testing need deterministic decision inputs. |
| Angular 22 Nx modular monolith remains the likely POC default but architecture assessment is configurable. | The default supports the POC while allowing evidence to justify a different target architecture. |
| Source projects are local runtime inputs and are not committed. | The customized solution must support multiple read-only customer/reference repositories without embedding them in its Git history. |
| Scanner outputs and graph namespace are isolated by project ID. | Project-specific artifacts, future Neo4j nodes, Graphiti memory, decisions, backlog, Figma mappings, and generated output must not mix. |
| HealthClinic Dashboard is a YAML sample profile, not hardcoded application logic. | The deterministic scanner must remain reusable for arbitrary future source roots. |
| Project-to-file edges use `CONTAINS`; `CONTAINS_CONTROL` is reserved for file-hosted controls and components. | Graph edge semantics must distinguish repository structure from UI composition. |
| MVC view relationships require a static explicit view name and matching discovered Razor view. | Implicit MVC conventions cannot be connected deterministically without project-specific guessing. |
| API calls are owned only by a unique Angular owner in the same source file. | File-local ownership prevents incorrect cross-service API relationships. |
| Neo4j persists generic graph records keyed by project ID and graph ID. | Project-scoped idempotency prevents duplicate loads and cross-project collisions. |
| Neo4j relationships use the stable `GRAPH_REL` type with a queryable `type` property. | Relationship semantics remain preserved without dynamically constructing Cypher relationship types. |
| Project clearing requires matching repeated confirmation and label-scoped deletes. | A project operation must never become a database-wide delete. |
| Roslyn is an opt-in semantic provider; Tree-sitter remains the default syntax provider. | C# semantic analysis should enrich deterministic facts without requiring a legacy project build. |
| LSP is a future interactive boundary, not a batch-analysis dependency. | Batch analysis must not require an IDE or language server. |
| Roslyn semantic facts require an actual resolved Roslyn symbol before they are marked proven. | Syntax evidence alone must not be presented as semantic resolution. |
| Roslyn identities use fully qualified symbols, while matching Tree-sitter controller/action nodes requires same-file evidence. | This prevents namespace collisions without duplicating equivalent syntax and semantic findings. |
| A type becomes a DTO only when an action return or parameter references it. | The scanner must not misclassify every C# type as a model. |
| Return-type and property-owner graph labels are selected from the proven fact for the fully qualified identity. | A graph edge must not promote ordinary types, such as `System.String`, to DTOs. |
| Roslyn semantic identities use fully qualified CLR symbol names without C# keyword aliases. | Real local SDK validation must distinguish framework types such as `global::System.String` and keep graph nodes collision-free across namespaces and member owners. |
| Step 3B completes only after a real helper build and Roslyn-enabled fixture run on a local .NET SDK. | Python-only tests do not prove the local batch semantic path or the actual helper/compiler integration. |
| Create Knowledge Graph is a deterministic CLI orchestration workflow, not an LLM or agent-framework workflow. | Input validation, Tree-sitter/Roslyn analysis, graph validation, Neo4j loading, and status reporting are reproducible tool operations that must remain auditable and safe. |
| Create Knowledge Graph defaults to graph-only mode; Neo4j loading is explicit through `--load-neo4j`. | Customers can produce and review a project-isolated graph without database availability, while database configuration and connection failures remain controlled workflow outcomes. |
| Create Knowledge Graph has no delete path and only uses the existing project-scoped loader. | Creating or loading one project graph must never overwrite another project or issue a database-wide Neo4j delete. |
| Each native Tree-sitter extraction runs in an isolated child Python process using JSON input and argument-array invocation. | A native parser termination in one source file must not terminate the parent workflow or prevent a partial, evidence-backed graph from being written. |
| Isolated extraction failures are represented as structured skipped warnings and `failed_isolated` inventory status, never inferred facts. | Partial graphs must remain honest about unparsed files without exposing source content or worker tracebacks. |
| Neo4j loading is blocked when a graph run has isolated extraction warnings. | Partial graph results require explicit review before persistence; no approval override is implemented in this POC. |
| Isolated extraction workers bootstrap `PYTHONPATH` from the local module-derived `src` directory and use the repository root when present. | Child workers must import the local package reliably from clean source checkouts without requiring an editable installation, while remaining compatible with installed packages. |
| Worker import failures use `worker_startup_failed`; nonzero native parser exits remain `abnormal_exit`. | Safe, actionable diagnostics must distinguish bootstrap defects from source-specific native parser faults without retaining stderr or tracebacks. |
| The HealthClinic Dashboard graph is not approved for a Neo4j visual demo while `Views/Home/Index.cshtml` has an isolated HTML extraction warning. | The scoped graph is a useful partial result, but the warning must be reviewed or explicitly approved before loading project data into Neo4j. |
| The HealthClinic Dashboard Neo4j demo uses the existing `healthclinic-dashboard` YAML profile from the repository root. | Configuration-based selected paths exclude the known failing `Views/Home/Index.cshtml` without embedding HealthClinic-specific scope logic in the reusable engine. |
| `healthclinic-dashboard-clean-demo` is ready for Neo4j visual-demo loading after Docker is available. | Its validated run has zero extraction warnings, proven Dashboard relationships, and an unchanged full source-tree fingerprint; only the requested project graph may be loaded. |
| Profiles declare explicit scope metadata and scope type. | Reusable configuration must identify the customer-approved modernization boundary without application-specific logic in the engine. |
| Selected-flow runs retain a complete audit inventory while their graph includes only in-scope File nodes and normal Roslyn facts. | A customer graph must make its scope boundary visible and must not silently represent unselected source as in scope. |
| Proven dependencies on excluded semantic symbols use `OutOfScopeReference` and `DEPENDS_ON_OUT_OF_SCOPE`. | Cross-scope evidence must remain honest without expanding the selected modernization graph. |
| Neo4j visual-demo loading requires `scope_complete` coverage and zero extraction warnings. | An approved Dashboard flow may be loaded only when every selected file is successfully parsed or explicitly unsupported. |
| `healthclinic-dashboard-scope-demo-v3` is the approved Dashboard Neo4j visual-demo graph. | Its regenerated source-of-truth artifacts report 24 selected File nodes, 2,360 explicitly out-of-scope audited files, 11 total/review warnings, zero extraction warnings, scope-complete coverage, and an unchanged source-tree fingerprint. |
| Neo4j visual-demo loading is blocked until Docker Desktop provides a resolvable `docker` CLI. | Both required preflight commands failed before any `.env`, Docker Compose, graph workflow, or database operation, so no Neo4j load can be claimed. |
| Docker Desktop installation requires user completion before the Neo4j demo can proceed. | The approved winget command downloaded version 4.88.1, but the installer remains running and the Docker Desktop executable is absent; UAC or other installer interaction must not be bypassed. |
| Docker Desktop must be used from a refreshed VS Code terminal after installation. | Installation completed and the executable exists, but the current PowerShell session cannot resolve `docker`; the workflow must not bypass the refreshed `PATH` requirement with an absolute-path invocation. |
| The approved `healthclinic-dashboard-scope-demo-v3` graph is persisted in local Neo4j for the visual demo. | Docker Desktop and Compose were verified, the Roslyn-enabled workflow and `load_neo4j` stage succeeded, and Neo4j counts match the generated project-scoped graph: 123 nodes, 169 edges, and 27 warnings with no other project IDs present. |
| Understand Anything is limited to a local read-only viewer of a deterministic visualization copy. | The canonical Tree-sitter/Roslyn graph and Neo4j remain the source of truth; the adapter rejects incomplete or mixed-project input, retains evidence and warnings, and no Understand Anything analyzer, LLM output, or API token is used. |
| The Understand Anything export must assign every canonical node to one deterministic non-empty viewer layer. | Viewer v2.9.0 derives its structural canvas topology from `layers`; labels, source paths, and proven relationships provide sufficient evidence for a read-only customer layout without changing the canonical graph or invoking an LLM. |
| End-to-end context graphs use explicit UI-transform and backend/domain-data preservation roles. | The Angular 22 modernization boundary is UI-only; selected API, domain, and data context must remain read-only and never become generation candidates. |
| End-to-end endpoint links require Roslyn and unique route/action proof. | Static source strings alone do not justify inferred backend semantics; dynamic routes remain review warnings and no Neo4j or viewer claim is made when required CLI validation is unavailable. |
| Understand Anything viewer packages are installed once from a pinned official release and launched only from ignored local vendor files. | Customer-demo runtime must not contact GitHub or npm; the local package is verified for name, version, MIT license, executable, and upstream repository metadata. |
| Dashboard reporting data access is represented as EF/LINQ only when the selected repository source proves it. | `ReportsRepository` uses `Where`, `OrderBy`, and async LINQ terminals; no literal raw SQL is present, so the graph must not invent SQL or database tables. |
| Customer-facing graph branding is `Legacy Dashboard POC`. | Internal project IDs and evidence paths remain unchanged technical identifiers while viewer presentation is neutral and reusable. |
| Complete-application graph loading requires complete extraction coverage. | The full baseline keeps all discovered source in one isolated graph, but its 47 isolated extraction failures prevent Neo4j and viewer presentation until reviewed. |
| Native crash fallback distinguishes first-party conservative extraction from opaque dependencies. | A worker access violation is never successful Tree-sitter extraction; only objective generated, minified/tooling, dependency-path, or upstream library-header evidence may produce `OpaqueSource`. |
| Full-application coverage has three explicit states. | `partial_application_with_first_party_extraction_failures` blocks completion, `complete_application` has no opaque dependencies, and `complete_with_opaque_dependencies` retains verified dependency inventory without claiming semantic understanding. |
| A first-party crash fallback requires at least one literal source fact in addition to provenance. | A `ConservativeSource` marker alone is not meaningful extraction and remains an explicit failure; C#, JavaScript, and Razor fallbacks emit only directly visible declarations, assets, controls, routes, or API literals. |
| `/create-knowledge-graph` is an agent instruction over the existing deterministic CLI. | The command may resolve runtime parameters and report results, but it must never use an LLM to construct graph facts or create a competing graph pipeline. |
