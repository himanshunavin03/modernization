# ADR-007: API Gateway, BFF, and Existing API Integration

## Status

Selected Target Architecture

## Context

This decision applies the approved requirements and target enterprise policy without changing existing business API contracts.

## Decision

- Separate typed API clients from presentation code.
- Use typed Feature API clients over preserved contracts.
- Use functional interceptors for transport-wide concerns.
- Place an API Gateway in the target enterprise topology.
- Place a provider-neutral BFF behind the gateway.

## Alternatives Considered

- Gateway-Only Integration (EVALUATED_ALTERNATIVE): Selected enterprise target includes a BFF.
- Direct Browser-to-API Integration (EVALUATED_ALTERNATIVE): Target selects gateway and BFF.

## Why Selected

- Preserved backend contracts are stable integration boundaries.
- Four approved Dashboard contracts define the integration boundary.
- Authentication context, correlation, and technical error normalization belong at request boundaries.
- It centralizes ingress, security policy, routing, rate limits, governance, TLS, observability, and correlation without rewriting business APIs.
- The target boundary owns Angular-specific orchestration, aggregation, response shaping, DTO isolation, and backend isolation while preserving existing APIs behind it.

## Consequences

- Contract isolation
- Focused testing
- Compile-time contract use
- Central policy
- Central governance
- Consistent ingress policy
- Reduced browser orchestration
- Backend isolation

## Tradeoffs

- Avoid abstractions that hide HTTP semantics
- Types must remain aligned
- Business logic must remain in Feature services
- Additional operations
- Product remains unselected
- Additional service ownership
- No endpoints are designed yet
