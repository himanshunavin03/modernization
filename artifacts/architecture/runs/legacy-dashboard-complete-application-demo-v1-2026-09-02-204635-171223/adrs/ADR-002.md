# ADR-002: Standalone Domain-Oriented Frontend Architecture

## Status

Selected Target Architecture

## Context

This decision applies the approved requirements and target enterprise policy without changing existing business API contracts.

## Decision

- Use standalone components for target features.
- Align domain libraries to approved Feature boundaries.
- Create a shared accessible UI and token library.
- Separate orchestration pages from reusable presentation components where useful.
- Deliver one modular application organized by domain libraries.
- Build reusable accessible UI primitives with tokens and responsive rules.

## Alternatives Considered

- None.

## Why Selected

- Standalone composition is the modern Angular default and supports direct lazy routes.
- Stable Feature domains provide meaningful ownership and dependency boundaries.
- Reusable primitives support consistent delivery and later normalized design input.
- The Dashboard coordinates several services while reusable views can remain input/output focused.
- Strong boundaries are useful without distributed frontend deployment.
- A shared boundary supports consistency and future design input.

## Consequences

- Explicit dependencies
- Less configuration ceremony
- Clear ownership
- Controlled reuse
- Consistent UX
- Central accessibility patterns
- Testable UI
- Clear state ownership
- Coherent deployment
- Consistent UX

## Tradeoffs

- Teams must learn current composition patterns
- Avoid excessive library fragmentation
- Requires contribution governance
- Do not split trivial components mechanically
- Requires dependency discipline
- Requires governance and manual validation
