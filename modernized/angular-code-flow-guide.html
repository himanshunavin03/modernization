01 · Mental model

One shell, independent business features.

The code is organized by responsibility rather than placing every class in one application folder. The application owns startup and navigation. Each business feature owns its screens and state. Data-access libraries own backend contracts. Core platform code owns concerns shared across features.

01BrowserRequests the Angular application and chooses a route.
02App shellStarts Angular and renders navigation plus a router outlet.
03Lazy featureDownloads Dashboard or Doctor code only when its route is opened.
04Feature storeCoordinates loading, selection, errors, forms, and UI state.
05API clientBuilds typed HTTP requests using preserved legacy routes.
06Legacy APIReturns tenant-specific business data without backend replacement.
Simple analogy: the application shell is a shopping mall, routes are signs, lazy features are stores opened only when visited, stores manage their own activity, and API clients are the controlled delivery doors to backend services.

02 · Runtime walkthrough

What happens from startup to screen.

1

Angular starts

src/main.ts calls bootstrapApplication(AppComponent, appConfig). This is the modern standalone bootstrap style: no root NgModule is required.

Browser → main.ts → AppComponent → app.config.ts
2

Global providers are registered

app.config.ts registers the router, typed HTTP support, three functional interceptors, and runtime configuration. Central registration prevents every feature from configuring these concerns differently.

HTTP request → correlation ID → optional TenantId → error reporting → backend
3

The private shell stays stable

PrivateShellComponent renders the header, responsive menu, navigation, footer, and inner <router-outlet>. Its menu state is a Signal. Feature screens appear inside it without recreating the shell.

4

The requested feature loads lazily

app.routes.ts uses dynamic loadChildren imports for both /dashboard and /doctors. The compiled application contains separate Dashboard and Doctor chunks, reducing initial feature code.

/dashboard → import Dashboard routes /doctors → import Doctor Directory routes
5

The feature component creates a local store

Dashboard and Doctor components declare their stores in providers. Each routed screen gets state with a lifecycle tied to that component, avoiding accidental stale state shared across unrelated visits.

6

Tenant context is resolved once per active subscriber group

TenantContextService calls /api/users/current/tenant, validates the returned integer, and shares the latest value. Feature stores wait for that value before business API calls.

7

The typed client preserves API contracts

DashboardApiClient and DoctorApiClient own URLs, HTTP verbs, query parameters, request bodies, and response types. Components never construct backend requests directly.

8

Signals update the template

Stores expose Signals such as items, loading, errorMessage, and computed values. Templates use Angular control flow such as @if and @for. OnPush keeps rendering predictable.

03 · Business flows

How each implemented feature works.

Dashboard

Summary and reports

The Dashboard store combines tenant context with three API requests. Independent year Signals trigger report reloads through RxJS switchMap, which replaces obsolete requests when the selected year changes.

year Signal → Observable → tenant → API client → response → Signal → chart
Doctor list

Load, order, select, delete

The list component asks its store for the first page. The store requests four records, appends later pages, computes alphabetic display order, tracks selected IDs, and retains records that fail deletion.

Load more → pageCount → GET /api/doctors → append → computed sort
Doctor create

Validated typed form

The detail component uses one non-nullable Reactive Form. Six required controls gate the Add button. A selected image is converted to Base64 and sent inside the preserved Doctor request rather than inventing an upload endpoint.

form valid → store.save → tenant → POST /api/doctors → navigate to /doctors
Doctor edit

Load, patch, save

The :id route selects edit mode. The store loads the record; an Angular effect patches the form and preview; successful submission uses PUT and returns to the directory.

/doctors/3 → GET /api/doctors/3 → form.patchValue → PUT /api/doctors
Cross-cutting HTTP

Consistent request policy

The correlation interceptor identifies requests, the tenant interceptor adds TenantId only when requested through HTTP context, and the error interceptor reports failures before stores convert them into user messages.

Validation

Three confidence levels

Component tests verify rendering and interaction, store tests verify state transitions, API-client tests verify HTTP contracts, and Playwright verifies observable browser workflows.

04 · Architectural layers

Why the code is separated this way.

Application layer

apps/healthclinic-web

Owns startup, global configuration, shell layout, top-level routing, assets, build, and development proxy.

Solves: one composition point without mixing business-feature logic into bootstrap code.

Feature layer

libs/*/feature

Owns routed pages, templates, user interaction, and feature route declarations.

Solves: business screens can evolve and lazy-load independently.

State layer

libs/*/state

Owns Signals, computed values, request orchestration, loading/error status, pagination, and mutation coordination.

Solves: templates remain presentation-focused and API timing remains testable.

Data-access layer

libs/*/data-access

Owns TypeScript models and typed HttpClient calls to preserved backend contracts.

Solves: route strings and payload shapes have one controlled owner.

UI layer

libs/dashboard/ui

Owns reusable presentation components with typed Signal inputs and outputs.

Solves: repeated visual behavior is reusable without acquiring business/API responsibilities.

Core platform layer

libs/core/platform

Owns runtime settings, tenant context, interceptors, route-policy extension points, and logging.

Solves: cross-feature infrastructure is implemented once and injected consistently.

06 · Angular choices and benefits

What each Angular pattern solves.

Standalone components

Less module ceremony

Each component declares exactly what it imports. Features become easier to lazy-load, test, and move.

Signals

Clear synchronous UI state

A value such as loading() is readable directly in the template and updates consumers when changed.

computed()

No duplicated derived state

Alphabetic doctors and chart series are recalculated from source Signals, preventing manual synchronization bugs.

RxJS

Controlled asynchronous work

switchMap, concatMap, finalize, and cancellation/cleanup handle HTTP workflows that are more complex than a single value.

Reactive Forms

Explicit validation model

The Doctor form has typed controls and validators in TypeScript, making submit rules inspectable and testable.

Functional APIs

Small composable infrastructure

Functional interceptors and guards avoid unnecessary classes while still using dependency injection.

OnPush

Predictable rendering

Components update from explicit reactive inputs and state rather than broad incidental change checks.

Modern control flow

Readable templates

@if and @for make conditional and repeated UI structure direct and type-aware.

Lazy routes

Feature code on demand

Dashboard and Doctor implementation bundles are fetched when users navigate to them rather than being part of one feature-heavy initial bundle.

Typed HttpClient

Visible integration contracts

Methods state expected request and response shapes, while dedicated tests protect route and header compatibility.

Dependency injection

Replaceable dependencies

Components receive stores and stores receive clients/services, enabling focused tests with controlled substitutes.

Nx libraries

Scalable ownership boundaries

Feature, state, data-access, UI, and platform concerns can be governed and tested as separate projects.

07 · Honest implementation boundary

What exists now—and what does not.

Implemented in the reviewed code

  • Angular 22.1.4 standalone bootstrap and components
  • Nx application plus feature/state/data-access/UI/platform libraries
  • Feature-level lazy loading for Dashboard and Doctors
  • Signals, computed state, and RxJS interoperability
  • Typed HttpClient clients and functional interceptors
  • Tenant-aware preserved legacy API calls
  • Doctor typed Reactive Form and CRUD workflows
  • OnPush rendering and modern template control flow
  • Unit/component/API contract tests and Playwright E2E
  • Responsive and accessibility-oriented markup

Not implemented in this code

  • No Gateway or Backend-for-Frontend implementation; development currently proxies directly to the legacy API
  • No selected real identity/authorization provider; the route guard currently allows navigation
  • No Patient feature or /patients route; its Doctor scenario remains explicitly skipped
  • No per-page loadComponent split inside the Doctor feature
  • No Angular @defer blocks or router preloading strategy
  • No NgRx, microfrontends, or Module Federation
  • No Signal Forms migration; Doctor uses stable typed Reactive Forms
  • No separate file-upload endpoint; pictures use the preserved Base64 field
Important distinction: Nx project separation improves ownership, test scope, and dependency governance, but it does not automatically create browser lazy loading. The dynamic import() expressions in app.routes.ts create the actual runtime chunks.

A ten-minute walkthrough for the team.

1

Start with the six-box flow

Explain shell → lazy feature → store → API client → legacy API. This gives everyone a shared map before file details.

2

Show app.routes.ts

Use Dashboard and Doctors to demonstrate real feature-level lazy loading and why the shell remains small and stable.

3

Follow one Doctor request

Trace DoctorListComponent → DoctorDirectoryStore → TenantContextService → DoctorApiClient → interceptor → /api/doctors.

4

Show why tests exist beside each layer

Client tests protect backend compatibility, store tests protect state behavior, component tests protect UI rules, and Playwright protects customer-visible workflows.

Close with the boundary list
